## 2. The three candidates

None changes an arithmetic operation, operand, addition order, PRNG draw, draw count, or branch outcome.

### A. Memoize `motor_readout_indices` out of the per-fly-tick cue path — best evidence, lowest risk

`sensory.rs:79` rebuilds a `HashSet<u32>` from scratch inside `group_currents`, called from `cue_currents` (`sensory.rs:61`), which `Attempt::advance_tick` calls **once per cue per fly per tick** (`attempt.rs:360-366`). Each build chains four motor index vectors, four `graph.pathway(...)` `HashMap<String,_>` lookups (`graph.rs:206-211`) and three `groups.iter()` string-compare scans (`sensory.rs:96-123`); then `sensory.rs:88` does a `contains` per group index (122/128 for vision).

Volume: 2 cues × 20 flies × 3000 ticks = **120,000 rebuilds of a constant of the graph**. The profile attributes it directly: 84% of all `hashbrown`/`sip` samples sit under `group_currents ← cue_currents ← Attempt::step`, ~2.5% of the round (`diagnosis.md:99, 114-117`).

Change: compute once (`OnceLock<HashSet<u32>>` on `Graph`, or eagerly in `Graph::from_bytes`), return `&HashSet<u32>`. Only two call sites: `sensory.rs:79`, `attempt.rs:229`.

**Expected: 0.8–1.1 ms/tick ≈ 2.7–3.7% (≈ 2.4–3.3 s per attempt).** Bit-exact: the set is only read via `contains`, so the filtered index sequence, summed values and `BTreeMap` output ordering are unchanged; `Graph` is shared as `Arc` with no interior mutability, so the cache cannot diverge.

### B. Fuse the synaptic scale sweep into the membrane sweep, hoist the `silenced` test

`lif.rs:284-290` is a standalone pass over all 70,000 neurons that reads `synaptic_input[i]`, tests `self.silenced.get(i) == Some(&true)`, and writes back `0.0` or `*input * p.input_scale`. The next loop (`lif.rs:291-313`) reads the same element and repeats the same test. LLVM does not fuse these (loop fusion is off in the default Rust pipeline), so per fly-tick this is an extra 560 KB read + 560 KB write and 140,000 `Option` compares — on state that is 3.29 MB per fly (`brainArrayBytes`) × 20 flies = 65.8 MB, always out of cache.

Change: compute the scaled value in a register inside the membrane loop, store it once to `synaptic_input[i]`, use the register for `dv`; hoist `let ablated = !self.silenced.is_empty()`.

**Expected: 0.8–1.6 ms/tick ≈ 2.7–5.3%.** Lower end is the pure-bandwidth floor (1.12 MB at ~28 GB/s ≈ 40 µs/fly-tick); upper end includes the removed per-neuron branch.

Bit-exact: each element's expression and operand order are unchanged and no element reads another's value, so fusion cannot reorder an addition. Two invariants must survive: (i) a silenced neuron's `synaptic_input` is zeroed *after* delivery has scattered into it (`lif.rs:272-283` can write into a silenced target); (ii) a silenced neuron's `dv`/`can_spike`/`voltage`/`spikes`/`refractory` stay untouched by the membrane loop, retaining what `enforce_silencing` wrote (`lif.rs:191-203`). This is the only candidate that edits the numerically sensitive loop — the trace harness in §5 is non-optional for it.

### C. Stop computing `Body::contacts` twice per fly-tick

`Attempt::advance_tick` calls `fly.body.contacts(world)?` for the taste current (`attempt.rs:367`); `Body::step` calls `self.contacts(world)?` again (`body.rs:565`). Nothing between them mutates the body — `attempt.rs:368-378` touches only the brain. `contacts` is a pure function of `(&self.state, world)` (`body.rs:464-479`) running one or two parry3d `touching_hull` convex-hull queries (`body.rs:273-286`, `body.rs:351-361`) — exactly the bucket measured at 4.85% (`diagnosis.md:98`), now ~7.2%.

Change: pass the computed `BodyContacts` in; keep `Body::step`'s signature and add a delegating `Body::step_with_contacts` so lab/test callers are untouched.

**Expected: 0.5–0.75 ms/tick ≈ 1.8–2.5% (≈ 1.6–2.3 s)** — half of whatever share `Body::contacts`, as opposed to `Body::step`'s own surface/motion queries, holds in that bucket. Widest error bar of the three; §4 collapses it from your profile.

Bit-exact: a pure result is reused, no float op differs. The only surface is error ordering — `Body::step` returns early on a terminal body (`body.rs:523`) and on starvation (`body.rs:558`) before calling `contacts`, but from `Attempt`'s side that is already unobservable (`attempt.rs:349` skips terminal flies, and `attempt.rs:367` has already called `contacts`). The delegating wrapper keeps all other callers identical.

**Combined: ~4–8% of production, ≈ 4–7 s off a 90 s round.**

## 3. Existing bounds — what these cannot fix

- **Noise floor.** `lif.rs:246-255` draws 700k pairs/tick: 700k `ln`, `sqrt`, `sincos`, 1.4M PRNG draws. Isolation measured 0.77–0.85 ms/fly-tick shipped vs 0.04–0.13 for "PRNG draw + store only" (`diagnosis.md:126, 166-172`) → **~14 ms/tick ≈ ~42 s of the 90 s round is software transcendental math no bit-exact change can touch.** `761a36a` took the one free win there. Marsaglia polar (−28%) needs a different stream — your open decision, out of scope.
- **Unavoidable state traffic.** 3.29 MB per fly-tick × 60,000 fly-ticks ≈ 197 GB per attempt before B's sweeps. `dv`/`can_spike` are 630 KB per fly-tick of pure diagnostics but are public (`lif.rs:213`) and hashed by the equivalence harness, so they stay.
- **Edge work is already gone.** The 47,922,900,000-inspection upper bound (`neural-cost/README.md:9`) is now ~5.9×10⁸ actual deliveries. Don't spend effort here.
- **Worker scheduling is not the production bottleneck.** At most 2 chunks in flight (`attempt-worker.ts:274`) of `MAX_CHUNK_TICKS = 10` (`record.rs:22`), credits returned on chunk receipt independently of the playback cursor (`attempt-client.ts:17, 86-89`) — the producer never idles, so production time maps ~1:1 into startup wait. The per-tick `await yieldToMessages()` (`attempt-worker.ts:115`) is ~3000 task turns ≈ <0.1 s of 90 s, and it is what bounds cancellation to one tick. **Leave it, the per-tick `JSON.parse(core.step())`, and the 10-tick cadence alone.**
- **The failing gate at HEAD is frame time, not production** — 34 ms p95 vs the 25 ms gate (`startup-delivery/README.md:10-11`), main-thread/renderer, in a run with other work active. A/B/C do not address it.
- **Startup has a non-compute component** — that run waited 11.183 s beyond the hindsight-earliest safe launch (`startup-delivery/README.md:16-21`). Policy, not CPU.

**Bottom line: A+B+C are a single-digit-percent win, comparable to `761a36a`. They do not close the startup target. The only large remaining lever is still the noise-stream decision.**
